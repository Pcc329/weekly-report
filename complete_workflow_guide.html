1

需求訪談

core/ · 想清楚要做什麼(與工具無關)

最大的失敗不是做錯,是還沒想清楚就開始做。這階段用一場 AI 訪談,把腦中模糊的念頭逼成一份可執行的說明書。不用先讀完整套方法論,訪談會帶著你走。

STEP 1

跑啟動訪談

打開 core/project-kickoff-interview.md,把提示詞整份複製,貼給任何一個 AI。它會分五輪問你:目標與成敗、利害關係人、系統現況、環境設定、限制與禁區。

為什麼答「不知道」也可以? 新手最大的焦慮是「不知道自己不知道什麼」。訪談把未知變成一張清單,焦慮就變成了待辦——這比假裝都懂安全得多。
你這個專案的 SETUP.md 初稿
STEP 2

存放並持續維護

把 SETUP 初稿存進 instances/<你的專案>/。之後每次工作告一段落就回來更新它——它是活文件,不是一次寫完的報告。不確定填到什麼程度?看 example-project 的示範。

↓ 想清楚了,開始做
2

AI 協作開發

core/ · 一個 PM 帶兩個 AI,規劃→執行→雙審查

關鍵原則:同一個 AI 不能從頭做到尾——規劃、執行、審查共用同一套盲點,等於沒有審查。所以把角色拆開,即使工具只有一個,也開不同對話分別扮演。

角色

三方各司其職

你(PM)=需求定義、範圍決策、最終驗收,唯一有拍板權。規劃 AI=把需求轉成規格書、當第一道審查。執行 AI=依規格寫程式,不參與範圍決策。

工具可換,角色不可換。 只有一個 AI 工具時,開三個獨立對話分別扮演即可;重點是規劃、執行、審查別讓同一個腦袋球員兼裁判。
STEP 3

寫規格書 → 執行 → 推分支

規劃 AI 依固定範本產出規格書(目標、範圍、禁區、驗收標準),執行 AI 照著做、每個功能開一條分支,回傳完成報告時必附 commit hash。

為什麼一功能一分支? 分支是主線的安全副本,改壞了不影響正在跑的版本;而 commit hash 是審查對照實際程式碼的唯一依據,沒有它審查是空的。
一條分支 + 完成報告(含 commit hash)
STEP 4

兩道檢查,問不同的問題

檢查一(規劃 AI＋你):對照規格逐項核對——「做出來的符合規格嗎?」檢查二(換一家廠牌的 AI):不給它結論,盲測——「規格本身有沒有更好的做法?」

為什麼檢查二要換一家? 不同廠牌模型的盲點不同。換一家取得的是「異質視角」——你買的不是算力,是另一組會問「為什麼要這樣做」的眼睛。
↓ 東西做好、審查過了,推上線
3

工具實作部署

tools/ · GitHub + Vercel,把東西真正搭起來、跑在網路上

前兩階段與工具無關,這階段才碰具體工具。目標不是「學會 GitHub」,是「照著點就能把東西部署上線」的最短路徑。全程在瀏覽器,不裝任何軟體。

STEP 5

GitHub:把東西放上去

Fork 一份現成的當起點,或開自己的 repo。網頁三招就夠用:鉛筆改檔、資料夾名/ 建資料夾、改檔名欄搬移。

為什麼放 GitHub 不存電腦? 交接時給一個網址就好,而且它自動記錄每次改動,誰何時改了什麼、出錯能還原。個人專案是保險,交接專案是必需。
STEP 6

分支與 PR:合併是人的最後一關

改動走一條分支 → 開 PR(合併申請)→ 先在預覽環境驗收 → 由你親手按 Merge 上線。兩個 AI 說 OK 不等於 OK。

為什麼 Merge 一定人來按? Merge = 上線,責任在人。你按下去那一刻,是在說「我看過、我負責」——這是拍板權,不可委派給任何 AI。
STEP 7

Vercel:改完自動上線

GitHub 連上 Vercel,從此 push 即自動部署。金鑰放環境變數(絕不寫進程式碼);開分支時 Vercel 自動生Preview 網址,驗收就看它。

為什麼金鑰放環境變數? 程式碼在 GitHub 上是公開的,金鑰寫進去等於公開。放環境變數,程式碼裡只有代號,別人看到原始碼也拿不到金鑰。

踩雷排除

tools/04-troubleshooting.md 是一張「症狀→原因→解法」對照表,卡住時 Ctrl+F 查。core/core/ 巢狀、Preview 打不開、環境變數沒生效……常見的坑都在裡面。

這條路徑會越走越順的原因

每次踩到「這個坑不是這個專案獨有,換個專案也會遇到」的時候,就把它從專案層(instances)搬進通用層(core / tools)。方法論不是寫完的文件,是用出來的紀律——你走得越多,它對下一個人越有用。
