三、機密性（Confidentiality）——防止不該看到的人看到資料

今天完成2項

  1. 搜尋引擎索引防護已完成：新增robots.txt與noindex標籤，明確告知搜尋引擎不要收錄。這是「請求」不是「強制」，正派搜尋引擎會遵守，但不影響知道網址者直接存取
  2. 後端金鑰洩漏查證已完成：全站掃描確認`SUPABASE_SERVICE_ROLE_KEY`只出現在後端程式，沒有意外流出到瀏覽器可讀取的檔案，結果乾淨
  3. API無身分驗證未處理，最大缺口：知道網址即可呼叫任何API，這是機密性最根本的破口，其餘機密性問題多數是這個問題的延伸
  4. 欄位白名單為唯一防線現況未變：資料庫層防護（RLS）對後端無效，因後端使用能繞過RLS的萬能鑰匙，程式碼白名單是唯一實質防線

四、完整性（Integrity）——確保資料不被竄改、保持正確

今天完成1項，同時查出既有良好實踐

  1. AI回答內容XSS消毒已完成，本次最重要發現：AI搜尋/AI分析功能的回答內容，轉換成HTML顯示前沒有經過任何檢查，理論上有機會被注入能在使用者瀏覽器裡執行的惡意程式碼。已加上DOMPurify消毒，實測正常格式（粗體、清單）保留，危險標籤被移除
  2. 寫入端點盤點已完成查證：確認全站僅`api/feedback.js`一支寫入端點，已有欄位驗證與白名單限制，本次額外加上流量管制（見下方可用性）
  3. 既有資料治理實踐已達標，非本次新增：mark-don't-delete原則、信心層級標示、PR前先核對實際diff不採信口頭回報，這些既有習慣本身就是良好的完整性實踐
  4. 備份可還原性演練尚未執行：每週有備份，但從未實際測試復原流程是否真的可用
展開細節
marked套件只負責markdown轉HTML語法轉換，不負責清理危險標籤。`index.html`（AI問答）與`compare.html`（AI比較分析）皆有`marked.parse()`輸出直接以`innerHTML`/`dangerouslySetInnerHTML`渲染的情況，已改為`DOMPurify.sanitize(marked.parse(...))`。`manufacturing.html`查證後確認AI分析結果已正確使用`escapeHtml`，不受影響；該檔案內有一個未被呼叫的`renderMarkdown`死代碼函式，本次未處理。
