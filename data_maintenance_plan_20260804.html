POST-MIGRATION DATA GOVERNANCE

切換後資料維護與權限規劃

資料庫切換改變的不只是「網站去哪裡拿資料」，也改變了資料在哪裡更新、由誰更新。 本規劃採「單一資料源 + 過渡期保險」架構：日常維護全數移至 Supabase， Airtable 保留兩席作為回滾保險，並訂定三個月後的退場條件，避免過渡狀態長期化。

適用：Supabase 正式切換後 期程：三個月 狀態：定案（餘 1 項待查） 2026-08-04

一、切換改變了什麼

先釐清一個常見誤解：Airtable 不會被停用，它只是不再是網站的資料來源。

切換前

維護人員編輯 → Airtable → 網站讀取 → 使用者看到 ✓ 全線相通

切換後（若未調整維護方式）

維護人員編輯 → Airtable ✗ 斷點：網站已不讀此處 Supabase → 網站讀取 → 使用者看到 ✓

這不是故障，是遷移完成後必然出現的狀況

任何系統從 A 資料源搬到 B 資料源都會遇到同一件事：讀取端切走了，寫入端還留在原地。 Airtable 資料完整保留、帳號照常可登入，只是在其中所做的修改不會反映到網站上。 本規劃即在把寫入端接回去。

二、兩種「權限」的區別

本規劃中最容易混淆之處，先行釐清。這也是同仁不需要 Supabase 後台帳號、卻仍能維護資料的原因。

為何不採後台帳號

Supabase 後台角色最低一級為 Developer，其權限說明已明確包含刪除資料，且無更低選項可選。 若循此途徑，同仁將具備刪除全表記錄的能力。 改由資料庫層授權可繞開此限制，將權限精確切分至所需範圍。

三、席次與權限配置

Airtable｜過渡期保險

對象席次用途
PM保留回滾操作、資料匯出備份
組長保留過渡期查閱
同仁拔除改由 Supabase 維護

保留席次是為了回滾能力，而非保存資料。 Airtable 免費方案上限為每個 base 1,000 筆，現行 base 約 4,310 筆；降為免費方案後 base 將轉為唯讀，回滾路徑即失效。 資料本身在任何方案下都不會被刪除。Airtable 依編輯者席次計費，唯讀檢視者不計費，三席降兩席可直接減少支出。

Supabase｜正式維護環境

對象存取方式可執行不可執行
PM後台 Owner全部操作—
同仁資料庫連線
非後台成員		查詢、新增、修改刪除記錄、改表結構、存取 Contacts
組長不開放——
同仁的實際操作方式

以資料庫工具連線

使用 TablePlus、DBeaver 或 psql 等工具連線，不需登入 supabase.com，不佔組織席次，接觸不到專案設定與帳務。若嘗試刪除，資料庫直接回傳 42501 permission denied。

為何不給刪除權限

不可逆操作集中管理

Supabase 無 Airtable 的 Snapshot 還原機制，誤刪後若無備份即無法復原。改錯可再改回，刪除不可逆。此與專案既有 ETL 安全流程（DRY_RUN → 小批次驗證 → 全量執行）採同一套邏輯。

組長不開放帳號的理由：實際需求為查看資料現況與統計，網站 dashboard 已可滿足，不需進入資料庫層。 減少一個具寫入能力的帳號，同時降低操作風險與管理成本。

四、開通時點：先收後放

角色建立腳本已備置完成，但不預先開通。

時點動作
現在SQL 腳本備置完成，不執行
同仁提出維護需求時執行腳本、設定密碼、提供連線資訊（約 1 分鐘）
同仁不再參與時執行 DROP ROLE，一步結束，不需變更其他設定

先收後放的兩個理由

其一，權限開了用不到，比要用時沒有更難處理。 其二，開通與升級 Pro（取得每日備份）兩件事的時點可自然對齊—— 同仁開始寫入資料時，正是備份保障開始重要的時候。

五、三個月期程

階段一 · 切換後約 1 週

凍結期：確認系統穩定

暫停資料異動，專注觀察系統運作。此期間若發生問題，可確定與資料變更無關，排查範圍單純。同時向同仁與組長說明凍結範圍與預計期限。

階段二 · 凍結期後約 11 週

正式維護

Supabase 為唯一維護入口，Airtable 僅供查閱與回滾備援。同仁依實際需求開通資料庫連線。

階段三 · 第 3 個月末

檢討與調整

依實際運作狀況決定 Airtable 是否退場、是否導入 MCP。此時已累積足夠運作經驗，可作出有依據的判斷。

六、退場條件

為避免過渡狀態長期化，明訂 Airtable 訂閱的退場條件。

1

Supabase 穩定運作滿三個月

期間無需執行回滾

2

完整資料備份已匯出並存檔

停止訂閱前完成，不於需要時才處理

3

同仁維護流程已穩定運作

確認 Supabase 路徑可完全取代原有作業

三項同時成立後停止訂閱。屆時 base 轉為唯讀，資料仍保留可讀，僅無法新增編輯。

七、MCP 導入時機

組長已於其他計畫使用 MCP，後期可透過 MCP 讀取本專案資料，不需再使用 Airtable。

但導入應在觀察期之後

專案既定的三項 MCP 觸發條件中，「Supabase 遷移完成」目前尚未達成。 系統尚未穩定時加接一層，問題發生時將難以判斷來源為遷移或 MCP。 觀察期間組長的查閱方式：直接使用網站 dashboard，不需資料庫權限。

Supabase Pro 的唯一必要理由是每日自動備份

「加成員」此一理由已不成立——同仁走資料庫連線，不佔組織席次。 考量無 Snapshot 還原機制，備份保障的優先序較高。 建議升級時點：同仁開通寫入權限時同步升級，兩者時點對齊。升級判斷應為需求觸發，而非預先購買。
