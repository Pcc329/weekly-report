**版本**：v3
**制訂日期**：2026-08-24（v2更新 2026-08-25：新增GCIS API日期欄位空值陷阱；v3更新 2026-09-30：新增第七節稽核節奏、第十節名稱比對方法與已知陷阱，並修訂第二、四、五、六、九節。同日更正：原稿曾誤將SME AI平台的差異歸因為「卡片標題截斷」，經驗證為官網一張商品卡對應資料庫多筆方案層級記錄，已於第六、十節更正）
**內部俗稱**：海巡
**適用範圍**：產業資料庫（solutions / companies / cases）所有來源網站的存活性與內容一致性稽核

---

## 一、目的與定義

資料新鮮度稽核，是指定期或觸發式地檢查資料庫中記錄的**來源仍然有效**，涵蓋兩個層次：

1. **來源存活性檢查**：來源網站/平台本身是否還在運作
2. **內容一致性檢查**：DB 裡的紀錄內容是否仍與來源網站現況相符

這兩層要分開判斷，不能混為一談——網站存活不代表內容沒變（例如方案下架但網站還在），網站掛了也不代表方案本身消失（例如平台轉移到別的網址）。

---

## 二、觸發時機

例行節奏見第七節（每週輕量檢查＋每月完整稽核）。除例行節奏外，以下情況應**額外觸發**稽核：

- **例行比對任務中的異常訊號**：例如本次是在做商業署117筆比對時，意外發現大量「查無」，追查後才發現是臺灣雲市集全站停站的連帶效應。任何一次批次驗證任務中，如果異常比例明顯偏高（例如超過預期的10~20%），應停下來先查是不是有更上層的系統性原因，而不是逐筆當作個案處理
- **單一來源佔比過大**：某個 `program_type` / 來源平台佔全庫比例顯著（例如臺灣雲市集佔全庫近半），該來源的健康狀況應優先、定期關注
- **外部消息**：政策公告、計畫結束消息、平台轉移公告等
- **長期未稽核的來源**：已納入第七節每週輕量檢查；新增來源平台上線時，於首次輕量檢查建立筆數基準

## 三、來源分級標準（判斷「完整目錄」vs「精選頁」）

這是最容易踩坑的一步。**商業署 service-ai.php 教訓**：該頁面實測只有18筆「精選」內容，無分頁、無動態載入，卻被誤用來比對DB裡完整117筆資料，產生大量假性「查無」。

### 判斷一個來源頁面是否為「完整目錄」，檢查以下訊號：

| 訊號 | 完整目錄特徵 | 精選頁特徵 |
|---|---|---|
| 分頁機制 | 有分頁/載入更多 | 無分頁，一頁到底 |
| 筆數規模 | 與官方公告的總量級數相符 | 明顯遠少於已知總量 |
| 更新頻率宣告 | 網站說明「即時更新」「完整名單」 | 網站說明「精選」「推薦」「熱門」 |
| 排序邏輯 | 依編號/日期等結構化欄位排序 | 依人工編輯順序或無明顯邏輯 |

### 判斷原則

- **優先使用官方「入選名單」「核定公告」類 PDF 或正式清單**，而非網站上的動態展示頁面。動態展示頁面通常是行銷用途的子集，不代表資料庫全貌
- 若無法取得官方完整名單，**必須先用小樣本測試**：抓幾筆已知一定在名單內的記錄，去該頁面確認能否查到，若查不到，該頁面不可信，禁止拿來做批次比對判準
- 判斷過程與依據，應記錄在稽核log中，供未來查核

## 四、標記信心分級（record_status 的誠實揭露原則）

核心原則：**用欄位值本身誠實揭露驗證的確信程度，不要用單一「已下架」蓋括所有情境。**

### 分級對照

| record_status 值 | 使用時機 | 驗證方式 |
|---|---|---|
| `已下架_<原因>` | 已針對該筆記錄**逐筆**確認來源失效（例如有 website_url 且實際訪問確認失效） | 逐筆驗證，高信心 |
| `疑似已下架_<原因>未逐筆驗證` | 有強力的**政策層級**證據（例如整個平台公告停止服務），但該筆記錄本身缺乏可逐筆驗證的線索（例如無 website_url） | 政策推論，中信心，需標明「未逐筆驗證」 |
| （不變更） | 弱訊號佐證（例如公司登記狀態查詢結果），不足以支持狀態判斷 | 寫入 `solution_status_log` 留痕，不動 record_status |

### 判斷邏輯範例

1. **臺灣雲市集停站案例**：153筆有 website_url 可逐筆驗證 → 標記 `已下架_平台停止服務`；1069筆無 website_url 無法逐筆驗證 → 標記 `疑似已下架_平台停止服務未逐筆驗證`。同一政策事件，依驗證能力分兩種信心層級標記，不能一視同仁
2. **GCIS批次弱驗證案例**：查到28家公司已解散，但這只是**間接佐證**（公司解散≠方案一定停止銷售，也可能是公司改組、方案由其他實體延續），信心強度不足以支撐狀態升級，因此**不改動 record_status**，只寫入稽核log供人工複核參考
3. **禁止的做法**：不可用「時間到期」自動把 `疑似已下架` 升級為 `已下架`。時間流逝不等於驗證，這樣做等於用猜測冒充確認，違反本節核心原則
4. **恢復（疑似 → 正常）需有逐筆證據**：例如該筆記錄的商品頁編號／網址在來源目錄中仍存在。2026-09-30 農業雲市集案例：9/21 依名稱比對標記的 17 筆疑似中，5 筆經編號比對確認頁面仍在架（只是改名），已恢復為正常並更新名稱，留痕於 `solution_status_log`。名稱比對造成的誤標，應以更強的證據修正，而不是放著不管

## 五、驗證留痕要求

每一次稽核任務，無論結果是否需要改動 record_status，都應留下可追溯的紀錄，包含：

1. **稽核觸發原因**：為什麼做這次稽核（哪個任務發現異常、或例行排程）
2. **判斷依據**：用了哪個來源（官方PDF/官網/API），為什麼認定該來源可信（依第三節分級標準）
3. **驗證範圍與方法**：查了多少筆、用什麼方式（逐筆人工/程式化批次查詢）
4. **結果分布**：各分類的筆數統計
5. **弱訊號的處理方式**：如果訊號不足以支撐狀態變更，記錄在哪（例如 `solution_status_log`），並說明「僅供輔助佐證，未變更record_status」

### 留痕位置

- **政策層級的重大發現**（如全站停站）：記錄在 `freshness-audit-log.md`
- **單筆或小批量的狀態變更原因**：記錄在 Supabase `solution_status_log` 表（`solution_id, status_change, reason, changed_at`）
- **每週輕量檢查**：記錄在 `freshness-audit-log.md` 的「每週輕量檢查紀錄」表格，一週一列；有異常才另開日期段落
- **週報摘要**：一句話結論 + 影響範圍，放進週報，不需要重複貼全部細節

## 七、稽核節奏（2026-09-30 定案）

原則：分兩層，強度不同、頻率不同。若每週都做完整稽核，成本過高，容易淪為說好每週、實際做不下去。（2026-09-21 僅稽核 3 個來源就耗時大半天；且 8/25→9/21 近一個月內新創嚴選僅 16 筆、農業雲市集僅 17 筆異動，逐週完整比對多數週會是「無異動」。）

### 第一層：每週輕量檢查（每週五，約 15～30 分鐘）

只回答兩個問題：**來源還活著嗎？官網總筆數與基準相比變了嗎？** 不逐筆比對名稱。各來源取得總筆數的方式與目前基準，見 `freshness-audit-log.md` 的「每週輕量檢查紀錄」。

| 檢查結果 | 處置 |
|---|---|
| 存活，且筆數＝基準 | 在紀錄表新增一列「無異動」，結束 |
| 存活，但筆數≠基準（任一方向） | 該來源**提前啟動完整稽核**（不等月度），完成後更新基準 |
| 無法連線／HTTP 4xx-5xx／導向他站／頁面標示停止服務 | 視為存活異常。先查有無全站公告（比照 2026-08-20 臺灣雲市集案例）；查證前**不標記**任何 record_status |

### 第二層：每月完整稽核（每月第三個週五前後，約半天至一天）

對已建立「完整目錄」基準的來源，依第三～五節流程與第十節的方法優先順序（有編號先用編號），做**逐筆**比對。同時產出兩份結果：（1）疑似下架／改名清單；（2）**收錄候選清單**（官網有、資料庫尚無的商品，交 ETL 評估，不屬於下架標記）。

**已知盲區（第二層不可省略的原因）**：輕量檢查只比總筆數。若同一段期間內「一筆下架＋一筆新上架」，總筆數不變，會被判為無異動；方案改名亦然。這類變化只有月度名單比對抓得到。因此對外說明時應講「**每週監測、每月完整稽核**」，不可只講「每週稽核」。

### 範圍與例外

- 內部資料（資策會產業調查、案例反推補建）無外部來源，不在稽核範圍
- 臺灣雲市集已確認全站停止服務：每月確認一次是否仍停站即可，不納入每週檢查
- 尚無筆數基準的來源（政府軟體採購網；新北產業AI化輔導計畫）：首次輕量檢查僅建立基準。新北需先處理 8/25 遺留的「官方公告 45 家 vs 資料庫 56 筆」落差，以完整稽核方式進行
- 頻率為預設值：實際執行 4～6 週後，依「無異動比例」與耗時再檢討

### 責任與留痕

- 執行：PPC（或指派協作者；需瀏覽器的來源使用 Claude for Chrome）
- 每次輕量檢查在紀錄表新增一列；完整稽核照第五節新增日期段落

## 八、GCIS API 已知技術陷阱：日期欄位空值不是null

**發現時間**：2026-08-25，GCIS弱驗證28家「已解散或廢止」複核時發現。

### 問題描述

GCIS「公司登記基本資料」API裡，`Revoke_App_Date`（廢止日期）、`Sus_Beg_Date`（停業起始日）、`Sus_End_Date`（停業結束日）這幾個日期欄位，當公司**沒有**相關紀錄時，回傳的**不是`null`**，而是一串**全形空白字元**（例如`"　　　　"`）。

Python判斷「這個值是否存在」時，一串空白字元屬於truthy（視為「有內容」），如果程式邏輯只寫`if revoke_date:`這種寫法，會誤判為「有廢止日期」，即使`Company_Status_Desc`欄位明明顯示「核准設立」（代表公司存續）。

### 實際影響

8/24首次執行GCIS弱驗證時，1069筆中有25筆solution（對應13個不重複統編）因此被誤判為「已解散或廢止」，實際上這13家公司都是「存續」狀態。修正耗費三輪除錯才完全排除（第一輪只修了revoke_date、漏了sus_beg/sus_end；第二輪程式碼傳遞疏失；第三輪才完整生效）。

### 正確處理方式

任何使用這支API的日期欄位做判斷邏輯，都必須先做**strip清理**再判斷是否為None：

```python
def clean_field(v):
    """統一清理欄位值：None或空白字元都視為無內容"""
    if v is None:
        return None
    s = str(v).strip()
    return s if s else None

revoke_date = clean_field(rec.get("Revoke_App_Date"))
sus_beg = clean_field(rec.get("Sus_Beg_Date"))
sus_end = clean_field(rec.get("Sus_End_Date"))
```

**通則**：此API所有日期類欄位都可能有這個問題，未來只要用到新的日期欄位（例如`Company_Setup_Date`），比照辦理先做清理，不要假設空值一定是`null`。

## 十、名稱比對的方法優先順序與已知陷阱（2026-09-30 新增並更正）

### 方法優先順序

逐筆比對資料庫與官網時，依可靠度由高到低：

1. **編號／網址比對**：資料庫若存有逐筆商品頁網址且含編號，先用編號。名稱會被平台改寫，編號不會。
   - 農業雲市集：`solutions.website_url` 含 `Content/{編號}`，93／93 可用
   - **使用前先查覆蓋率**：新創嚴選網 145 筆中資料庫網址為商品 UUID 者僅 1 筆（其餘並非逐筆商品連結），不可用；SME AI 平台 279 筆資料庫網址全為空，不可用。覆蓋率不足就退回第 2 項，不要硬做
2. **名稱正規化後精確比對**：移除控制字元與所有空白、統一全形半形標點、轉小寫，資料庫端與官網端套用**同一套**正規化
3. **模糊比對**：僅作為線索，不可直接作為標記依據

編號比對的判讀：

| 結果 | 意義 | 處置 |
|---|---|---|
| 同編號、同名 | 正常 | — |
| 同編號、不同名 | 頁面仍在，名稱被改。名稱與功能相近 → 視為改名；差異大 → **不可僅憑名稱判定**，該頁面可能改放了其他商品，需核對內文 | 改名：更新名稱（必要時恢復狀態）；不確定：維持疑似並留痕，待核對 |
| 編號不在官網清單 | 頁面已從清單消失 | 疑似已下架；若能直接開啟該頁面確認失效，才可升為 `已下架_*` |
| 官網有、資料庫無該編號 | 新商品，或「同名商品換編號重新上架」 | 先以名稱查是否為換編號，是則更新網址；否則列入收錄候選 |

### 已知陷阱

1. **官網一個商品，資料庫多筆方案層級記錄（一對多）**：SME AI 平台官網每個商品一張卡，資料庫則把同一商品的每個方案（「方案一／二」「100 人版／200 人版」「PRO／標準版」）拆成獨立記錄，名稱帶方案後綴。2026-09-30 查明 27 筆差異中 23 筆屬此類、3 筆為標點差異、僅 1 筆（Genie CPO）確實不在官網。帳目：資料庫 279 － 官網 266 ＝ 13 ＝（方案記錄 21 － 商品卡 10）＋ JOO 系列 2。處置：以「官網商品」為單位判斷存在性，容許「資料庫名稱＝官網名稱＋方案後綴」的一對多對應。
   - **更正**：2026-09-21 稽核曾將此現象誤判為「列表卡片標題被截斷」。9/30 驗證 266 張卡片標題與詳情頁標題**逐筆完全一致**，並無截斷。結論（這些不是下架）不變，但成因說明作廢
2. **平台自行改寫商品名稱，造成名稱比對誤標**：2026-09-21 農業雲市集以名稱比對標記 17 筆疑似，9/30 編號比對顯示其中 5 筆頁面仍在架、僅改名（誤標約 3 成），且當時列出的十餘筆「官網有、資料庫無」新增候選，幾乎全是這些改名。**名稱比對的標記應視為線索，有編號可用時必須以編號複核**
3. **隱形字元與亂碼**：`SOL-1207` 名稱含 U+000B（**官網標題本身如此**，非本庫髒資料）；`SOL-0498` 的「™」被存成「?」（ETL 亂碼副本）。處置：比對前先正規化；不因官網來源含隱形字元而修改本庫名稱
4. **標點、全半形、空白差異**：如「Lale協會雲-」與「Lale協會雲」、逗號後有無空格。處置：同上
5. **CSV 欄位含逗號未加引號**：2026-09-21 匯出檔中「(Pest Detection System, PDS)」被切成兩欄，造成假性「查無」。處置：匯出時所有欄位一律加引號，解析後核對筆數
6. **同公司疑似改名，以整家公司為單位比對**：2026-09-30 律果案例——資料庫 4 筆、官網 3 筆，兩兩比較會漏看第三筆。列出該公司資料庫全部方案與官網該公司全部方案再對照
7. **手動搬運清單造成的假差異**：2026-09-30 將官網清單手動抄進查詢時，「預警系統」抄成「預警服務」，憑空製造一組差異。處置：清單由程式產生後直接複製；出現孤立的單筆差異時，先懷疑搬運錯誤，並以第二種方法（例如編號）交叉驗證再下結論
8. **來源自身的錯誤，不在本庫的責任範圍**：官網簡介與內文主題不一致（律果合約專家專業方案：簡介為電子簽名文案，內文為合約管理）、標題含隱形字元等，屬來源平台的問題。**原則：不投入時間替來源平台勘誤，只處理「本庫是否因此誤導使用者」**。例：`SOL-1367` 的簡介改採官網內文重點，原簡介完整留存於 `solution_status_log`

### 判斷原則

- 差異呈現**單一、一致的模式**（例如 26:1）時，優先懷疑方法論而非資料，先查機制再決定標記——**但也要驗證自己提出的機制**：2026-09-21 的「卡片截斷」解釋當時未驗證，事後證明是錯的
- 比例只決定「值不值得先查」，**不能取代逐筆判斷**
- 標記前先問：這個結論靠的是名稱，還是靠編號？靠名稱的，信心降一級
